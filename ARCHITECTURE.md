# Project Black Lantern Architecture

## Status

This document is the architectural source of truth for the handwritten Godot project.

It defines runtime ownership, scene flow, feature boundaries, file organization, UI composition, state lifetimes, and the finite ten-floor expedition structure. `NORTH_STAR.md` remains the product-design authority; this document describes how the game is organized to deliver it.

## Core Decisions

- Use a feature-first project structure.
- Build production UI with Godot scenes and reusable component scenes.
- Keep visual tokens and shared control styles centralized.
- Use one scene-scoped `DungeonRunManager` as the authoritative owner of an active run.
- Keep run state private; change it through manager methods and read it through getters.
- Keep event and battle dialogs local to the active dungeon screen.
- Keep pause and screen transitions in a global overlay layer.
- Make dungeon rules data-driven, including the ten-floor limit.
- Keep generated Chisel data isolated from handwritten code.
- Avoid a project-wide `GameManager`; `DungeonRunManager` exists only for the lifetime of `DungeonScreen`.

## Application Flow

```text
Main Menu
    -> Overworld Town
    -> Dungeon Selection Map
    -> Dungeon Expedition
        -> Explore
        -> Resolve Event or Battle
        -> Continue
        -> Extract, Die, or Complete Floor 10
    -> Run Results
    -> Overworld Town
```

The three valid expedition endings are:

- `EXTRACTED`: the player leaves early and secures eligible gains.
- `DEFEATED`: the player loses the expedition and resolves loss-protection rules.
- `COMPLETED`: the player resolves floor 10 and finishes the dungeon.

All endings use the same results pipeline before returning to town.

## Application Shell

The eventual `GameRoot` owns screen navigation and global overlays:

```text
GameRoot
|-- ScreenHost
|   `-- CurrentScreen
`-- GlobalOverlayLayer
    |-- PauseMenu
    `-- ScreenTransition
```

`SceneRouter` replaces the child of `ScreenHost`. Feature scenes do not navigate by loading arbitrary scene paths themselves; they request a destination through the router.

Until `GameRoot` exists, `bootstrap.tscn` may continue loading the main menu directly.

## Feature Boundaries

Each feature owns its screens, controllers, feature-specific UI, and local state helpers.

### Main Menu

The main menu begins or resumes the application flow. It must not own expedition state.

### Overworld Town

The town is the persistent hub. It presents secured inventory, unlocks, services, and entrances to other overworld features.

Town systems read and update `ProfileState`. They never mutate an active encounter directly.

### Dungeon Selection Map

The overworld map presents available dungeon definitions. Selecting a destination creates a `DungeonRunConfig` from the selected definition, a deterministic seed, and the player's starting run values. The application flow injects that config into `DungeonRunManager` before starting the dungeon.

Map markers reference dungeon IDs, not scene paths or hardcoded event pools.

### Dungeon Expedition

The dungeon feature owns exploration, floor progression, run inventory, encounters, extraction, and completion.

Its root composition is:

```text
DungeonScreen
|-- ExplorationMap
|-- DungeonHUD
|   `-- InfoPane
`-- EncounterLayer
    |-- EventDialog
    `-- BattleDialog
```

The `EncounterLayer` displays at most one encounter interface at a time.

## Runtime State Ownership

### ProfileState

Lifetime: across expeditions and application sessions.

Owns:

- Secured items and currency
- Town progression
- Unlocked heroes and dungeons
- Permanent discoveries and codex knowledge
- Settings that belong in the save profile

### DungeonRunConfig

Lifetime: immutable input to one dungeon run.

It contains the selected dungeon ID, deterministic run seed, maximum floors, starting player values, and the dungeon's map-generation profile. The dungeon-selection flow creates it; UI nodes do not.

### DungeonRunManager

Lifetime: exactly the lifetime of `DungeonScreen`.

It owns the mutable truth needed by the dungeon feature: current floor, player life, immutable run configuration, and the authoritative raw board. The prototype intentionally keeps this state in the manager instead of introducing a separate expedition-state model.

Its fields stay private. Other dungeon nodes issue commands through methods, read snapshots through getters, and listen to signals such as `player_died`. Generator scripts return raw board data to the manager; the map receives only a render copy.

### Encounter State

Lifetime: one event or battle.

Owns only the information needed to resolve that encounter. Its result is applied through `DungeonRunManager`, after which the encounter state is discarded.

UI controls never become the authoritative store for profile, run, or encounter data.

## Dungeon Run Manager

`DungeonRunManager` is attached to the root of `DungeonScreen`. It is global only within that scene.

Its narrow responsibility is to:

- Store the run configuration, current floor, player life, and authoritative board
- Call a supplied floor-generator `Callable`
- Apply validated state changes through manager methods
- Give the map a copied board snapshot for rendering
- Receive map intent and expose it as manager-level signals
- Emit one-time events such as `player_died`

The manager does not render tiles, interpret mouse input, or contain the floor-generation algorithm.

### Generator and Map Flow

A generator is an ordinary script method. No inheritance hierarchy or framework interface is required. The caller can provide it as a `Callable`:

```gdscript
run_manager.start_run(run_config, floor_generator.generate)
```

Temporary prototype bootstrap: until dungeon selection exists, `DungeonRunManager._ready()` calls `start_run()` with a hardcoded config and `PrototypeFloorGenerator.generate`. Remove that bootstrap call and config when the real selection flow supplies them; the public `start_run()` API remains unchanged.

For each floor, the manager copies the run configuration, adds the current floor, calls the generator, and stores the returned `Dictionary` as its authoritative board. It then calls `map_view.render_board(board_snapshot)`.

The map keeps only that copied render data. It emits `action_requested(action, payload)` when the player interacts with it. `DungeonRunManager` receives the signal and exposes `map_action_requested` for listeners. Gameplay code responds by calling a manager command; the map never edits or replaces the board itself.

```text
Map input
    -> action_requested
    -> DungeonRunManager command
    -> authoritative board mutation
    -> render_board(copied snapshot)
    -> Map display
```

This keeps the manager authoritative while allowing generation and gameplay rules to remain small callable scripts.

## Ten-Floor Contract

The vertical-slice dungeon is finite.

- A dungeon definition supplies `maximum_floors`.
- The initial vertical-slice value is `10`.
- Floor progression is one-based.
- No system may create or navigate to floor 11.
- Floors 1 through 9 may offer extraction or descent according to content rules.
- Resolving the terminal objective on floor 10 produces `COMPLETED`.
- Extraction, defeat, and completion all create a `RunResult` and return through the same results flow.

The floor limit belongs in the dungeon definition or expedition rules, never in a label, button, map tile, or dialog script.

## Encounters

### Illustrated Events

The event controller resolves requirements, choices, deterministic outcomes, and state changes. `event_dialog.tscn` renders the event and emits player intent.

The dialog must not directly award items, change floors, or edit profile state.

### Battles

The battle controller owns turn order, cards, energy, enemy intent, statuses, and battle resolution. `battle_dialog.tscn` renders combat and emits commands.

Battle results are returned to `DungeonRunManager`, which applies them to the run.

## UI Architecture

Production UI is composed in `.tscn` scenes so layout, assets, animation, anchors, containers, focus order, and embellishments remain editable in Godot.

### Shared Theme

`game/ui/theme/ui_theme.gd` remains the token and style library for:

- Palette
- Typography scale
- Spacing
- Sizing
- Border and radius values
- Reusable style construction

The planned `game_theme.tres` becomes the default Theme assigned at the application or screen root. It should define named theme variations such as:

- `TabButton`
- `PrimaryButton`
- `OrnatePanel`
- `ModalFrame`
- `CharacterStatsHeader`

Components select a semantic variation rather than repeating raw colors, margins, font sizes, and StyleBoxes per instance.

### Reusable Components

Feature-agnostic visual building blocks live in `game/ui/components/`. Examples include ornate frames, tab buttons, modal frames, resource counters, and localized tooltip controls.

Feature-specific compositions remain beside their feature. `InfoPane` belongs to `features/dungeon/ui/`, even when it uses shared tab and frame components.

Decorative frames and corners should use `NinePatchRect`, `StyleBoxTexture`, and small overlay textures where appropriate. They should not be recreated procedurally in every screen script.

### Programmatic UI Helper

`game/ui/ui.gd` is a Flutter-inspired GDScript builder, not a Flutter runtime.

It may remain for disposable prototypes, tooltips, localization helpers, and genuinely runtime-generated controls. Do not expand it into a second production layout system. Existing production screens should migrate toward `.tscn` composition when they receive their next visual pass.

### UI Behavior Rule

Scenes own composition. Scripts own behavior and data binding. Theme resources own presentation tokens and control states.

## Data and Content

Handwritten content definitions belong under `game/content/` as Godot Resources when they require editor-authored references or composition.

Chisel-generated assets, localization, tables, input bindings, and manifests remain under `game_data/`. The `.chisel/` directory remains Chisel-owned project state.

Rules:

- Never manually edit files marked `Generated by Chisel`.
- Never move generated files into feature directories.
- Handwritten code may read generated classes and assets.
- Generated code must not import or depend on feature scenes.
- Chisel exports should be reproducible without overwriting handwritten files.

## Save Boundaries

When run saving is added, `DungeonRunManager` must produce a plain-data snapshot. The save system serializes that snapshot rather than serializing the scene tree or UI nodes.

Recommended checkpoints are:

- After persistent town changes
- When an expedition starts
- On room entry
- After event resolution
- After battle resolution
- On floor transition
- On extraction, defeat, or completion

Store deterministic seeds and unresolved choice state so loading cannot reroll pending outcomes.

## Dependency Direction

Dependencies flow inward toward stable data and systems:

```text
Dungeon UI -> DungeonRunManager -> Content Definitions / Map Generator
Encounter UI -> Encounter Controller -> DungeonRunManager
Shared UI -> Theme / Localization
Features -> Cross-feature Systems
Handwritten Code -> Chisel-Generated Data
```

Disallowed dependencies include:

- Generated data importing feature code
- Shared UI importing a specific feature
- Profile state depending on scene nodes
- Event or battle dialogs changing application screens directly
- Feature controllers reaching into another feature's scene tree

## Naming Rules

- Files and folders use `snake_case`.
- Feature root scenes use a clear role suffix: `town_screen.tscn`, `dungeon_screen.tscn`.
- Reusable UI scenes use the visual role: `tab_button.tscn`, `ornate_panel.tscn`.
- The scene-scoped run authority is named `dungeon_run_manager.gd`; controllers describe narrower workflows such as `battle_controller.gd`.
- State and data classes use explicit suffixes: `DungeonRunConfig`, `FloorGenerationConfig`, `RunResult`.
- Avoid generic names such as `Manager`, `Helper`, or `Utils` unless the responsibility and lifetime are narrow and documented. `DungeonRunManager` is the intentional scene-scoped exception.

## Architectural Completion Checks

A change follows this architecture when:

- Its state has one clear owner and lifetime.
- Mutable dungeon-run state is private to `DungeonRunManager`.
- Only `DungeonRunManager` initiates floor generation and supplies its derived floor config.
- The map stores only render data and emits player intent; it never mutates the authoritative board.
- Its scene lives with the feature that owns it.
- Reusable UI is feature-agnostic before moving to the shared UI directory.
- Visual constants come from the shared theme system.
- Generated Chisel directories remain untouched by handwritten changes.
- Dungeon progression cannot exceed the configured floor maximum.
- Event, battle, pause, and navigation responsibilities remain separate.
- UI emits intent instead of directly mutating authoritative state.
